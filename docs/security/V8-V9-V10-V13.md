# V8, V9, V10 and V13 – Dilnuk De Silva (IT22001252)

## V8 – Secrets committed to the repository (OWASP A05 / A07, CWE-798 / CWE-312)

**What was wrong.** Several credentials had been committed to the public repository:

- `backend/.idea/dataSources.xml` held a full MongoDB Atlas connection string with the database
  user and password. `.idea` was listed in `.gitignore`, but the folder had been committed before
  the rule was added, and git keeps tracking files it already knows about.
- The Firebase web config was hardcoded in `employee-management/services/firebase.js`.
- An OpenWeather API key was hardcoded in both `driverAnalytics.jsx` pages.
- EmailJS service, template and public IDs were left in comments in `ApplicantAccept.jsx`.

We found these with **gitleaks** (scanning both the working tree and the full git history) and by
grepping `git log -p` for connection strings and keys.

**Why it matters.** Anyone who clones or browses the repo gets direct access to the production
database (every salary, NIC and CV) without touching the application at all. The API keys can be
abused on our quota and billing.

**How we fixed it (commit `458e5db`).**
- `git rm --cached backend/.idea`, so the existing ignore rule finally applies.
- Firebase and OpenWeather keys are read from Vite environment variables (`VITE_*`); the EmailJS
  identifiers were redacted.
- `backend/.env.example` and `frontend/.env.example` document which variables are needed, without
  real values.
- `backend/config/env.js` makes the server **fail fast**: it refuses to start if `DATABASE_URL` or
  `SECRET` is missing, or if `SECRET` is shorter than 32 characters.

**Why deleting the file is not enough.** The old values are still in git history, and anyone can
check out an older commit. Rewriting published history would break every existing clone and the
commit record that shows our fixes. The correct response to a leaked secret is to **rotate** it:
generate a new password or key and revoke the old one, so the leaked value is useless.

**How to prove it.** Running gitleaks on the current tree reports 0 findings (it reported 1 before).
The new CI `security` job runs gitleaks on every push, so a new leak fails the build.

## V9 – Vulnerable and outdated dependencies (OWASP A06, CWE-1104 / CWE-1035)

**What was wrong.** `npm audit` / `pnpm audit` before the fix:

- **Backend: 28 advisories** (2 critical, 13 high), including arbitrary file overwrite in `tar`
  (pulled in by `bcrypt` → `node-pre-gyp`), an HMAC bypass in `jws`, ReDoS in `path-to-regexp`,
  and an arbitrary-upload issue in `connect-multiparty`.
- **Frontend: 246 advisories** (8 critical), including `jspdf` and `axios` issues, and server-only
  packages (`mongoose`, `fs`, `dotenv`, `cloudinary`) that were bundled into the browser app for
  no reason.

**How we fixed it (commit `4a4ea67`).**
- Backend: `npm audit fix`; **`bcrypt` → `bcryptjs`**. `bcryptjs` is pure JavaScript with the same
  API, so the native build chain (and its vulnerable `tar` / `node-pre-gyp`) is gone completely.
  Upgraded `nodemailer`, removed unused packages.
- Frontend: removed unused and server-only packages (a browser app should never ship a database
  driver), and upgraded `axios`, `jspdf`, `firebase` and `react-router-dom`. The `jspdf-autotable`
  v5 upgrade needed the plugin to be registered in `main.jsx`, otherwise the 19 PDF report exports
  would have broken.

**Result.** Backend **28 → 0**. Frontend **246 → 2 moderate**; the remaining two are transitive and
have no patched release in a compatible version range, so they are documented as not fixed.
We checked that the Vite build still succeeds and PDF exports still work.

**How to prove it.** `npm audit` in `backend/` reports 0 vulnerabilities. The CI `security` job
runs `npm audit --audit-level=high` so a new high or critical advisory fails the build.

## V10 – Unrestricted file upload (OWASP A04, CWE-434)

**What was wrong.** `express-form-data` was applied globally (`app.use(formData.parse())`), so
**every** endpoint accepted multipart uploads and wrote them to disk, even endpoints that never
expected a file. The photo handlers saved `req.files.<field>.path`, a path built from the
client-supplied filename, with no check on type, size or name. An attacker could upload HTML, SVG
with script, or an executable, and its path was stored in the profile.

**How we fixed it (commit `2cc9724`).** Removed `express-form-data` (and its vulnerable
`connect-multiparty` dependency) and added `backend/middleware/upload.js` using multer:
- only **JPEG, PNG or WebP** (anything else → HTTP 400);
- **2 MB** maximum and **one file** per request;
- **random UUID file names**, so the client cannot choose the path or overwrite another file;
- stored in `backend/uploads/`, **outside the web root** and ignored by git;
- only the routes that need a photo use the upload middleware; the vehicle form uses
  `textOnlyForm`, which accepts text fields and rejects any file.

**How to prove it.** A PNG upload returns 201 with a UUID name; an HTML file sent as `photo`
returns 400 "Only JPEG, PNG or WebP images are allowed".

## V13 – Unauthenticated `/send-email` (open mail relay) (OWASP A01 / A04, CWE-306)

**What was wrong.** `POST /send-email` took `to`, `subject` and `text` from the request body and
sent the email through the estate's Gmail account using nodemailer, with no login, no role check
and no recipient check. It was outside `/api`, so the auth middleware never reached it. Transport
errors were also sent back to the client as-is.

**Why it matters.** This is an **open relay**: anyone on the internet could send spam or phishing
that really comes from the estate's address. That damages trust, and Gmail would suspend or
blacklist the account, breaking legitimate emails too. The scanners did not report it; we found it
by reading `server.js`.

**How we fixed it (commit `01f94c0`).**
- The route now uses `decodeUserFromToken` and `requireRole(...MANAGERS)`, so only a logged-in
  manager can send (the repair module's manager screen is its only caller).
- The recipient must be a single email address, otherwise HTTP 400.
- Transport errors are logged on the server and the client gets a generic message.

**How to prove it.** `security-tests/poc.sh` check "V13 /send-email refuses anonymous callers"
sends a spam request without a token and expects HTTP 401.
